## 1. 这是什么

`news.html`(卡片版 A,进导航「动态」)与 `news-c.html`(聚合版 C,noindex + canonical 指 A)两页同源多源信息流:
八个内容源 → AI 加工(筛选/锐评/简报译题/全文翻译/概念抽取)→ 静态详情页 `news/p/<id>.html` + 概念页 `news/c/<slug>.html`。
管线是 `build_news.py`(单文件,增量,可安全反复运行);定时靠 `.github/workflows/news-cron.yml` 每 6 小时。

**当前八源**:rui 博客 / 公众号(飞书登记表闸门) / 产品动态 / 媒体报道 / 行业动态(5 路 RSS) / 大咖观点(8 路 RSS) / Hacker News / 齐思。
**已下线源**:Wechaty(2026-07-07,开发者向内容对官网受众是噪音)、**企微生态 wecom(2026-07-27,佳芮:企微不出现在任何页面)**——两者恢复/删除的痕迹都在 build_news.py 注释里。

## 2. 架构裁决(为什么长这样,别推翻)

**方向 1:生成物不进 git**(2026-07-23 佳芮裁决,PR#103 的核心重构)。
仓库只留「配方」:`build_news.py` + 两个 workflow + 页面模板壳 + 人工种子(`data/product-news.json`、`data/press-news.json`)。
`news/`、`data/news.json`、`data/concepts.json`、`data/render-cache.json`、`data/news-content/` 全部 gitignore。

数据流(**状态以服务器为准闭环**):
```
CI 每 6h:  rsync 拉服务器 /opt/www/jz-news/{data,news}/ → 跑 build_news.py(增量) → rsync --delete 推回
           不 commit、不 push、仓库零机器提交
对外路由:  nginx 把 /news.html /news-c.html /news/ 指到 /opt/www/jz-news/(data/ 不对外)
```
被否掉的两条路(别走回头路):①生成物入库(仓库膨胀 + 每天 4 个机器 commit 和人的分支互相 rebase);②Git LFS(只解决图片体积,没解决生成物入库这件事本身;且免费额度 1GB/月会撞限)。

### 一条方法论教训

这一轮连续三次差点因为**用便宜的代理指标替代真实测量**而下错结论：

1. 静态 `grep <nav>` → 误判「377 个页面转化路径为零」（导航是 `site.js` 运行时注入的）
2. `len(summary)` 当内容指纹 → 等长替换（「企业微信」→「自有阵地」）识别不出，缓存跳过
3. 看截图判横向溢出 → 实为 headless 最小窗口宽度限制（`--window-size=390` 实际 `vw=492`），
   截图裁掉了 102px，布局本身零溢出

**下结论前先量。** 三态计数（`written/same/skipped`）之所以有价值，正是因为它逼着
每一页都落到某一态里，不给「看起来没问题」留空间——它两次报出的 `written` 数
（链接规范化 9、schema 修复 6）都与独立统计的问题页数精确吻合。

## 6.8 keep_max 修剪：审查报的 high 不成立，但隐患真实（2026-07-30）

独立审查报了个 high：`keep_max` 修剪把超额上站条目整条删掉，而它们仍在 feed 窗口内，
于是「删掉→重抓→重判→重译→再删」每 6 小时循环一次，持续烧 AI 配额。

**实测推翻。** 直接抓 feed 量窗口：

| feed | 条数 | 窗口跨度 |
|---|---|---|
| 量子位 | 10 | **1 天** |
| 雷锋网 | 20 | **1 天** |
| 36氪 | 30 | 日期不可解析（同类日更源） |

而 `industry` 上站 100 条覆盖 07-22 ~ 07-29，削顶边界在 **8 天前**。被削掉的条目
根本不在 feed 里，不可能被重抓。审查者是把代码注释里「个人博客 feed 窗口横跨数年」
那句话的场景，套到了日更新闻源上。

**隐患仍然真实，只是没触发。** `voices`（大咖观点）是个人博客源，feed 窗口确实可能
横跨数年，当前上站 **88/100**，到顶那天就会开始重复付费。

**试过墓碑方案，已回退。** 超额条目不整条删、只留 id/url/date/source/ai 的瘦身墓碑，
让去重表认出它以免重抓。实测确实生效（48 条墓碑保留 AI 判定），但引入了更糟的副作用：
墓碑剥掉了展示字段 → **不可逆**，`voices` 上站从 88 掉到 40，`keep_max` 调回 100
也回不去。为一个未触发的隐患换一个正在发生的缺陷，是净损失。

**保留的是日志拆分**（纯收益）。原来一行 `[修剪] 36 条` 把两类混成一个数字，现在是：

```
[修剪] 共 48 条 = 上站超额 48(其中 48 条已花过 AI 成本) + 过 45 天保留期 0
```

隐患真发生那天，「已花过 AI 成本」这个数字会直接把它指出来。**与其加一层猜测性防护，
不如让问题发生时无法被忽略。**

**真到那天怎么修**：多半是调整 `voices` 的 `keep_max` 或改为不设限——大咖观点这类内容
长期有价值，对它设存量上限本身就值得商榷。那是产品决策，不该由工程单方面定。
另注：`keep_max` 的原始动机是「不修剪会让内联数据无限膨胀」，而内联膨胀问题已被数据
分片（`news-radar.json`）解决，这个上限的存在理由本身也该重新评估。

## 6.9 两条架构纪律（2026-07-30，从这轮的重复踩坑里提出来）

### 一、同一语义写两遍必然漂移 —— 已出现五次

| 语义 | 曾分散在 | 后果 |
|---|---|---|
| 哪些概念够格发独立页 | 4 处（漏了第 4 处） | **64 条死链**长期存在无人发现 |
| 详情页是否允许收录 | 3 处（sitemap 漏 `mirror_on()`、ItemList 用错常量） | sitemap 会收 noindex 页；ItemList 向 AI 引擎公示 5 条 noindex URL |
| 什么算「提到了这个概念」 | 2 套规则（`str.find` vs `concept_rx`） | 漏证据（`RLHF` 匹配不到 `rlhf`）＋误证据（`api` 命中 `rapid`） |
| live region 该挂在哪 | 2 页各写一遍 | 聚合版每次筛选让屏幕阅读器重念 20 篇全文 |

**五次都不是粗心，是结构问题**：判断散落在调用点上，没人能保证它们同步演化。现已全部收口：

- `worthy_concepts()` — 概念够格标准，四处共用，另有管线内死链断言兜底
- `detail_indexable()` — 详情页可收录，详情页 robots／sitemap／ItemList 三处共用
- `concept_rx()` — 概念匹配规则，正文标注与证据抽取共用
- live region 统一挂计数元素（`#newsCount`），不套在内容容器上

**纪律**：新增任何「符合某条件的集合」判断前，先找现成函数；找不到就抽一个，不要在调用点另写一遍。判据分散的代价是**静默的**——它不会报错，只会在某个分支下悄悄给出不同答案。

### 二、验证器的默认值决定它的偏向

这轮跑过一次多维度对抗审查（5 个独立审查员 + 每个发现由另一个 agent 试图证伪）。结果：

- **它找到了我几十轮自审完全没触及的问题**，包括 4 个 high 和一条能让**首页掉出索引**的 canonical 传导
- **但它的证伪判断，9 条里 9 条判错，全部偏向「放过真 bug」，零反向误报**

根因在我写的提示词：「宁可漏掉一个真问题，也不要让假问题浪费维护者的时间」＋「拿不准就判 refuted=true」。
这两句合起来，等于让证伪方**无需举证即可判死**。而代价从来不对称——**误报浪费的是我的时间，放过留下的是生产事故**。

**纪律**：要复用这套机制，把举证责任放在「判死」一方——判 refuted 必须给出可复现的反证（具体输入 → 具体输出证明不成立），存疑一律保留待人工看。它的输出只能当**候选清单**，不能当过滤器。

### 三、附带记一条：验证手段比被验证对象更弱时，「通过」只证明了盲区

这轮我自己的验证方法失效六次，每次都给出了错误的「通过」或「失败」：

1. 静态 `grep <nav>` → 误判「377 个页面转化路径为零」（导航是 `site.js` 运行时注入的）
2. `len(summary)` 当内容指纹 → 等长替换（「企业微信」→「自有阵地」）识别不出，缓存跳过该更新的页
3. 探针用错元素 id → 搜索压根没触发，却跑出两行「一致」
4. 只数条目数不看字段 → 墓碑实验剥掉 48 条记录的字段，「上站数恢复」这个指标通过了，但字段回不来，管线随后崩在 `KeyError`
5. `lstrip("www.")` → 在 `www.juzibot.com` 上恰好正确（测试数据全是它），`wow.example.com` 会被啃掉开头的 `w`
6. 检测正则不懂 script 标签属性 → 把 JSON 数据当 JS 报语法错，差点去改一个没坏的文件

**其中第 5 条最危险：它能通过我打算做的所有测试。** 偶然正确的写法比明显错误的更贵，因为它会被当成对的沿用下去。
