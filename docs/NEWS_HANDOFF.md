## 1. 这是什么

`news.html`(卡片版 A,进导航「动态」)与 `news-c.html`(聚合版 C,noindex + canonical 指 A)两页同源多源信息流:
八个内容源 → AI 加工(筛选/锐评/简报译题/全文翻译/概念抽取)→ 静态详情页 `news/p/<id>.html` + 概念页 `news/c/<slug>.html`。
管线是 `build_news.py`(单文件,增量,可安全反复运行);定时靠 `.github/workflows/news-cron.yml` 每 6 小时。

**当前八源**:rui 博客 / 公众号(飞书登记表闸门) / 产品动态 / 媒体报道 / 行业动态(5 路 RSS) / 大咖观点(8 路 RSS) / Hacker News / 齐思。
**已下线源**:Wechaty(2026-07-07,开发者向内容对官网受众是噪音)、**企微生态 wecom(2026-07-27,佳芮:企微不出现在任何页面)**——两者恢复/删除的痕迹都在 build_news.py 注释里。

## 2. 架构裁决(为什么长这样,别推翻)

**方向 1:生成物不进 git**(2026-07-23 佳芮裁决,PR#103 的核心重构)。
仓库只留「配方」:`build_news.py` + 两个 workflow + 页面模板壳 + 人工种子(`data/product-news.json`、`data/press-news.json`)。
`news/`、`data/news.json`、`data/concepts.json`、`data/render-cache.json`、`data/news-content/` 全部 gitignore。

数据流(**状态以服务器为准闭环**):
```
CI 每 6h:  rsync 拉服务器 /opt/www/jz-news/{data,news}/ → 跑 build_news.py(增量) → rsync --delete 推回
           不 commit、不 push、仓库零机器提交
对外路由:  nginx 把 /news.html /news-c.html /news/ 指到 /opt/www/jz-news/(data/ 不对外)
```
被否掉的两条路(别走回头路):①生成物入库(仓库膨胀 + 每天 4 个机器 commit 和人的分支互相 rebase);②Git LFS(只解决图片体积,没解决生成物入库这件事本身;且免费额度 1GB/月会撞限)。

### 两个「查了但决定不修」的（附判据，别重复挖）

**① 图片 alt / width-height（1870 个 `<img>`，99% 无尺寸、64% 无 alt）**

看着很吓人，实际不该动：

- **90% 落在 noindex 的第三方转载页上**
- **可被索引页面（35 个自家详情页）里无 alt 的图 = 0 个** —— 自家内容 100% 合规
- 缺的 alt 是第三方原文自己就没写。**不能编造**：给不知道内容的图写描述、
  或统一塞 `alt=""` 声称它是装饰性的，都是往页面上放假信息
- 缺的尺寸要修就得下载 1687 张远程热链图（`lilianweng.github.io` / `cdn.beekka.com`
  / `s.baoyu.io` …），存储 + 版权 + 维护成本远超收益

**② Font Awesome 153KB（最大单个资源，占传输量 37%）**

生成页只用 16 种图标（news.html 21 种），却扛完整字体，且走 jsdelivr 海外 CDN，
国内加载失败时图标会变方块。**但这是全站既定架构**——`index.html`、
`products/*.html`、`workforce/*.html`、`about.html` 全部同款引用，站内无自托管资源。

在动态页单独改会造成两套图标系统。**要动就全站一起动**，方案备选：
① 16-21 个图标换内联 SVG（约 6KB，省 150KB）；② 自托管子集化字体；
③ FA 的 CSS 异步加载（不减体积，只解阻塞）。这是全站基建决策，留给你拍板。

### 一条方法论教训

这一轮连续三次差点因为**用便宜的代理指标替代真实测量**而下错结论：

1. 静态 `grep <nav>` → 误判「377 个页面转化路径为零」（导航是 `site.js` 运行时注入的）
2. `len(summary)` 当内容指纹 → 等长替换（「企业微信」→「自有阵地」）识别不出，缓存跳过
3. 看截图判横向溢出 → 实为 headless 最小窗口宽度限制（`--window-size=390` 实际 `vw=492`），
   截图裁掉了 102px，布局本身零溢出

**下结论前先量。** 三态计数（`written/same/skipped`）之所以有价值，正是因为它逼着
每一页都落到某一态里，不给「看起来没问题」留空间——它两次报出的 `written` 数
（链接规范化 9、schema 修复 6）都与独立统计的问题页数精确吻合。

## 6.8 keep_max 修剪：审查报的 high 不成立，但隐患真实（2026-07-30）

独立审查报了个 high：`keep_max` 修剪把超额上站条目整条删掉，而它们仍在 feed 窗口内，
于是「删掉→重抓→重判→重译→再删」每 6 小时循环一次，持续烧 AI 配额。

**实测推翻。** 直接抓 feed 量窗口：

| feed | 条数 | 窗口跨度 |
|---|---|---|
| 量子位 | 10 | **1 天** |
| 雷锋网 | 20 | **1 天** |
| 36氪 | 30 | 日期不可解析（同类日更源） |

而 `industry` 上站 100 条覆盖 07-22 ~ 07-29，削顶边界在 **8 天前**。被削掉的条目
根本不在 feed 里，不可能被重抓。审查者是把代码注释里「个人博客 feed 窗口横跨数年」
那句话的场景，套到了日更新闻源上。

**隐患仍然真实，只是没触发。** `voices`（大咖观点）是个人博客源，feed 窗口确实可能
横跨数年，当前上站 **88/100**，到顶那天就会开始重复付费。

**试过墓碑方案，已回退。** 超额条目不整条删、只留 id/url/date/source/ai 的瘦身墓碑，
让去重表认出它以免重抓。实测确实生效（48 条墓碑保留 AI 判定），但引入了更糟的副作用：
墓碑剥掉了展示字段 → **不可逆**，`voices` 上站从 88 掉到 40，`keep_max` 调回 100
也回不去。为一个未触发的隐患换一个正在发生的缺陷，是净损失。

**保留的是日志拆分**（纯收益）。原来一行 `[修剪] 36 条` 把两类混成一个数字，现在是：

```
[修剪] 共 48 条 = 上站超额 48(其中 48 条已花过 AI 成本) + 过 45 天保留期 0
```

隐患真发生那天，「已花过 AI 成本」这个数字会直接把它指出来。**与其加一层猜测性防护，
不如让问题发生时无法被忽略。**

**真到那天怎么修**：多半是调整 `voices` 的 `keep_max` 或改为不设限——大咖观点这类内容
长期有价值，对它设存量上限本身就值得商榷。那是产品决策，不该由工程单方面定。
另注：`keep_max` 的原始动机是「不修剪会让内联数据无限膨胀」，而内联膨胀问题已被数据
分片（`news-radar.json`）解决，这个上限的存在理由本身也该重新评估。

## 6.9 两条架构纪律（2026-07-30，从这轮的重复踩坑里提出来）

### 一、同一语义写两遍必然漂移 —— 已出现五次

| 语义 | 曾分散在 | 后果 |
|---|---|---|
| 哪些概念够格发独立页 | 4 处（漏了第 4 处） | **64 条死链**长期存在无人发现 |
| 详情页是否允许收录 | 3 处（sitemap 漏 `mirror_on()`、ItemList 用错常量） | sitemap 会收 noindex 页；ItemList 向 AI 引擎公示 5 条 noindex URL |
| 什么算「提到了这个概念」 | 2 套规则（`str.find` vs `concept_rx`） | 漏证据（`RLHF` 匹配不到 `rlhf`）＋误证据（`api` 命中 `rapid`） |
| live region 该挂在哪 | 2 页各写一遍 | 聚合版每次筛选让屏幕阅读器重念 20 篇全文 |

**五次都不是粗心，是结构问题**：判断散落在调用点上，没人能保证它们同步演化。现已全部收口：

- `worthy_concepts()` — 概念够格标准，四处共用，另有管线内死链断言兜底
- `detail_indexable()` — 详情页可收录，详情页 robots／sitemap／ItemList 三处共用
- `concept_rx()` — 概念匹配规则，正文标注与证据抽取共用
- live region 统一挂计数元素（`#newsCount`），不套在内容容器上

**纪律**：新增任何「符合某条件的集合」判断前，先找现成函数；找不到就抽一个，不要在调用点另写一遍。判据分散的代价是**静默的**——它不会报错，只会在某个分支下悄悄给出不同答案。

### 二、验证器的默认值决定它的偏向

这轮跑过一次多维度对抗审查（5 个独立审查员 + 每个发现由另一个 agent 试图证伪）。结果：

- **它找到了我几十轮自审完全没触及的问题**，包括 4 个 high 和一条能让**首页掉出索引**的 canonical 传导
- **但它的证伪判断，9 条里 9 条判错，全部偏向「放过真 bug」，零反向误报**

根因在我写的提示词：「宁可漏掉一个真问题，也不要让假问题浪费维护者的时间」＋「拿不准就判 refuted=true」。
这两句合起来，等于让证伪方**无需举证即可判死**。而代价从来不对称——**误报浪费的是我的时间，放过留下的是生产事故**。

**纪律**：要复用这套机制，把举证责任放在「判死」一方——判 refuted 必须给出可复现的反证（具体输入 → 具体输出证明不成立），存疑一律保留待人工看。它的输出只能当**候选清单**，不能当过滤器。

### 四、改了实现就得改说明它的文字 —— 这一轮我犯了六次

| # | 漂移 | 后果 |
|---|---|---|
| 1 | `CLAUDE.md` 写「no lint/test」，而我加了 87 项测试 | 下一个人不会去跑，而那套测试刚抓到一个安全回归 |
| 2 | handoff §3 标着过期数据；我插说明时还把 §8 表格插断了 | 接手人第一眼看的就是这节 |
| 3 | README 缺 `test_build_news.py` 与 `--clean-shell` | 入口文档看不到「改渲染前该跑什么」 |
| 4 | PR 描述写着已撤的企微源 + 已废的 commit+push 部署 | **审阅者据此判断** |
| 5 | nginx 注释写「三条 location」（实际五条）、「252 概念页」（实际 109） | 读注释的人会以为配置不全 |
| 6 | `CLAUDE.md` 锐评定位仍写「编辑评论」，而页面已标注 AI 生成 | 口径自相矛盾 |

**共同形状：改了实现却没同步说明它的文字，而文字会被下一个人信任。**

这不是洁癖问题。今天真吃过亏：`worthy_concepts()` 的注释写「详情页标注／概念页生成／sitemap
**三处**必须用同一份」，而实际有四处——**我照着那份错清单去验证**，漏掉的第四处（概念页之间的
相关链接）挂了 64 条死链，长期无人发现。错的文档比没有文档更贵。

**纪律**：
1. 改任何实现，先问「哪份文字描述了它」——`CLAUDE.md`（长期规格）／本文（当下状态）／
   `README`（入口）／`DEPLOY.md`（上线手册）／PR 描述（审阅入口）／代码注释，逐个过。
2. **别在文档里写会过期的数字**，除非有测试钉住。今天删掉的 nginx「252 概念页」、改掉的
   handoff「07-29 实测」都是这么来的；产物清单能写死是因为 `test_build_news.py` 钉了四处。
3. **语义漂移没有自动办法**。曾加过一条「文档引用的路径必须存在」的检查，因 6 个误报删掉了
   （文档里的简称、示例、外部路径都会命中，而且我在实现里又误用了 `lstrip("./")`）。
   经常误报的检查等于没有检查，还会训练人忽略它。这条只能靠改代码时顺手改注释。

### 三、附带记一条：验证手段比被验证对象更弱时，「通过」只证明了盲区

这轮我自己的验证方法失效六次，每次都给出了错误的「通过」或「失败」：

1. 静态 `grep <nav>` → 误判「377 个页面转化路径为零」（导航是 `site.js` 运行时注入的）
2. `len(summary)` 当内容指纹 → 等长替换（「企业微信」→「自有阵地」）识别不出，缓存跳过该更新的页
3. 探针用错元素 id → 搜索压根没触发，却跑出两行「一致」
4. 只数条目数不看字段 → 墓碑实验剥掉 48 条记录的字段，「上站数恢复」这个指标通过了，但字段回不来，管线随后崩在 `KeyError`
5. `lstrip("www.")` → 在 `www.juzibot.com` 上恰好正确（测试数据全是它），`wow.example.com` 会被啃掉开头的 `w`
6. 检测正则不懂 script 标签属性 → 把 JSON 数据当 JS 报语法错，差点去改一个没坏的文件

**其中第 5 条最危险：它能通过我打算做的所有测试。** 偶然正确的写法比明显错误的更贵，因为它会被当成对的沿用下去。

## 6.10 一个安全回归，与它暴露的工作流缺陷（2026-07-30）

### 发生了什么

写完离线冒烟测试 `test_build_news.py`，**第一次跑就抓到 5 个失败**——全在消毒:
紧贴引号的事件属性绕过（`<img src="x"onerror="alert(1)">`）与 `style` 剥离**双双消失**，
XSS 通道又开了。

追溯提交:

```
bd387bd  消毒修复 ✓   ← 执行通道故障期间，直接在 feat 分支用 Edit 做的
4024aeb  修复丢失 ✗   ← 从 stage-2 拷 build_news.py 到 feat，覆盖掉了
```

### 根因: 工作流的单向性假设

常规流程是「在 stage-2 改 → 跑管线验证 → 拷到 feat 提交」，它**假设 stage-2 永远是更新的
一方**。而那段时间 Bash 分类器故障、无法跑管线，我只能用 Edit 直接改 feat，从未同步回
stage-2。之后一次反向拷贝就把修复抹掉了，**并且连带四次提交我都没察觉**。

**纪律**: 两个分支之间拷文件前，先确认哪一侧更新——`git log -S'<关键代码片段>' -- <文件>`
能直接查出某段代码在哪些提交出现/消失。凡在非常规路径（分类器故障、只读通道、直接 Edit）
上做过的改动，务必回头同步另一侧，否则它活不过下一次拷贝。

### 为什么四道守卫全都没拦住

这个回归躲过了当时**全部**验证手段:

| 守卫 | 为什么没拦住 |
|---|---|
| `shell-clean` CI | 只查模板壳是否混入生成数据 |
| `copy-guard` CI | 只查「企微/企业微信」文案口径 |
| 管线内守恒断言 | 只查页面计数守恒 |
| 管线内死链断言 | 只查概念页链接可达 |
| 全量重建 | **每次都成功、产物都正常** |

最后一条是关键: 存量镜像里恰好没有带 payload 的第三方内容，所以消毒逻辑退化后
**没有任何可观测症状**。产物正常不等于逻辑正确。

**只有针对不变量的测试能抓到它。**

### 因此新增 test_build_news.py

纯标准库、不联网、不需要 API key、秒级跑完。覆盖 10 组不变量，每组都对应一次真实修复:

1. noindex 页不发 Article/Breadcrumb schema
2. noindex 页 canonical 不得指向站内可收录页（曾指向首页）
3. 译题与原题一字不差时不渲染「原题：」
4. 详情页只标注够格发页的概念（曾留 64 条死链）
5. 公司区+雷达拼接后严格日期倒序（曾让「全部」分区时间流倒回）
6. SVG 不被判为可本地化图片（可内嵌 script，托管即存储型 XSS）
7. 消毒剥事件属性与 style，含紧贴引号/大写/无引号各变体
8. 链接规范化: 相对路径补全、mailto 与畸形协议降文本、**query 里带 `://` 的相对链接不误伤**
9. 模板源码指纹进版本键（改模板忘 bump 曾两次导致缓存跳过）
10. 原子写**失败路径**: 旧文件完好且不留 `.tmp`

**跑法**: `python3 test_build_news.py`（退出码非 0 即有回归）。改任何渲染/消毒/写入逻辑后
先跑它——比全量管线快两个数量级，且不依赖网络与密钥。

### 顺带一条: 这项目原本 no lint/test，为什么现在值得有

这轮我犯的错里有很大一部分是「改了但没验证」或「验证手段比被验证对象更弱」。而全量跑
一次要几分钟、需要网络与 `ZHIPU_API_KEY`，代价高到**「就改了个模板，先不验了」变成常态**。
测试的价值不在覆盖率，在于**把验证成本压到低于偷懒的诱惑**。

## 6.11 拷贝方向反了两次，两次都出事（2026-07-30）

今天有两次事故，根因**完全相同**——在预览分支(stage-2)与 PR 分支(feat)之间拷文件，方向反了:

| 事故 | 后果 |
|---|---|
| 从 stage-2 拷 `build_news.py` 回 feat | 抹掉了只在 feat 做过的**消毒修复**，XSS 通道重开，带着四次提交跑了一路 |
| 从 stage-2 拷 `news.html`/`news-c.html` 回 feat | 带回 103KB/245KB **注入数据**，违反「生成物不入库」——这已是第二次（首次是 eafb0e3 那批 223KB） |

### 正确方向只有一个

```
源码（build_news.py、模板壳、assets/*.js）在 feat 改
        ↓ 拷过去跑管线验证
    stage-2（产物入库是它的模式）
        ↓ 验证通过
   回 feat 提交（源码本来就在 feat，无需拷回）
```

**永远不需要 stage-2 → feat 的拷贝。** 需要拷回，说明改动做错了地方。

### 两条兜底

1. **拷文件前先确认哪侧更新**: `git log -S'<关键代码片段>' -- <文件>` 直接查出某段代码
   在哪些提交出现／消失。非常规路径（分类器故障、只读通道、直接 Edit）上做过的改动，
   务必回头同步另一侧，否则活不过下一次拷贝。
2. **万一还是拷回来了**: `python3 build_news.py --clean-shell` 一次还原两个页面的注入区，
   别手改正则（我手改过三次，每次都要重新想一遍要清哪几个标记）。

### CI 的两道闸都抓到了，但时机不同

- `shell-clean` 抓到了模板壳污染 —— **但我推送后才看结果**，中间已经污染了一次提交
- `news-test` 的不变量测试抓到了消毒回归 —— 那次是我主动写测试才发现的，
  在此之前四道守卫全都放过了它（详见 6.10）

**闸有效不等于防护有效，还得有人在推送前看。** 提交前本地跑一遍
`python3 test_build_news.py` 与 shell-clean 的同款检查，比事后修 CI 红灯便宜得多。
