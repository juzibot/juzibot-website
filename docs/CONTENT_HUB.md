## 为什么要有它

动态页八个源里四个靠人工投递，它们的入口是散的，而且**大多要开发者才碰得到**：

| 源 | 原入口 | 结果 |
|---|---|---|
| 公众号 | 飞书「发布登记」表 | 42 行，运营能自己动 |
| 产品动态 | `data/product-news.json` | 5 条，改一次找开发者 |
| 媒体报道 | `data/press-news.json` | **0 条，从没人录过** |
| 公司动态 | `data/company-news.json` | 20 条草稿，卡在口径确认 |

**媒体报道 0 条是最硬的证据**：不是公司没有媒体报道，是入口在 git 里，运营碰不到。
而唯一一个非开发者能自己动的源（公众号），恰好就是唯一一个有飞书表的源。

## 三个设计决策

**一 · 一张表，不按源拆表。** 运营的心智是「我要往动态页放一条内容」，不是
「我要往产品动态表放一条」。按源拆表是按系统实现分的，会先逼人做一道
「这该放哪」的选择题。代价是不同源字段不同——用「来源」单选 + 按来源的必填校验
解决，而不是拆表。

**二 · 状态必须回写。** 这是中台区别于原「发布登记」表的关键。原表**只有输入没有
反馈**：运营勾了「上官网」之后不知道到底上没上、什么时候上的、链接是什么，每次都得
问开发者。管线回写四件事：上站状态 / 站内链接 / 最后同步 / 管线消息。
**没有回写，中台就只是个提交箱。**

**三 · 口径检查前置。** 企微红线原先在 CI 才拦，而 CI 红的时候人已经在别的事上了，
非开发者也看不懂 CI。表里用公式字段当场标出来——建表当天就抓到一条
（《句子干货｜企业微信敏感词…》）。

## 不做什么（同样是设计）

- **不在表里编辑 HTML 正文。** 公司动态的 body 是 HTML 片段，多维表格没有 HTML
  编辑器，硬编辑只会产出坏 HTML。正文继续走飞书文档，表里放「正文文档」链接。
- **不做自动上站。**「上官网」是佳芮定的人工闸门，中台不绕过它。
- **不碰自动源。** 博客/行业/大咖/HN/齐思本来就不用人管，进中台只会添乱。
- **不让 build_news.py 直连中台。** 管线不该多一个必须联网+授权才能跑的依赖
  （CI 里没有 lark-cli，这是既定约束）。中台落到既有投递位，飞书挂了管线照常跑，
  降级成「内容不更新」而不是「管线跑不动」。

## 数据流

```
人在表里填 + 勾「上官网」
    ↓  python3 hub.py pull --apply
data/{product,press,company}-news.json   ← 既有投递位，格式一个字没改
    ↓  python3 build_news.py             ← 管线一个字没改
上站 → data/news.json
    ↓  python3 hub.py push --apply
表里「上站状态/站内链接/最后同步」变绿
```

## 字段（15 个，分三区）

**A 录入区（人填）**：标题 / 来源 / 原文链接 / 发布日期 / 摘要 / 分类 / 署名 / 正文文档
**B 闸门区**：上官网（唯一开关）/ 口径检查（公式，自动）/ 备注
**C 回写区（管线写，人别改）**：上站状态 / 站内链接 / 最后同步 / 管线消息

必填按来源分：公司动态要「标题+发布日期」（无站外原文），其余要「标题+原文链接」。

## 命令

```bash
python3 hub.py status          # 一屏看清各源卡在哪
python3 hub.py pull            # 中台 → 投递位（干跑）
python3 hub.py pull --apply
python3 hub.py push            # 管线状态 → 中台（干跑）
python3 hub.py push --apply
```

`push` 需要 `data/news.json`（管线产物），所以在有产物的环境跑（stage-2 或服务器）。

## 迁移与实测（2026-08）

67 行已迁入：产品 5 + 公司 20 + 公众号 42（媒体 0——这正是问题本身）。
push 实测回写 67 行，46 条「已上站」带站内链接、21 条「未提交」。

**两个实测才抓到的坑，都记在 hub.py 注释里：**

1. **写入毫秒、回读 ISO 字符串。** `ymd()` 第一版只处理数字，字符串走 `int()` 抛异常
   被 except 吞成空串 → 公司动态的 (标题,日期) 键全部对不上 → body 接回逻辑静默失效
   → **一次 pull 清空了二十篇月报的正文、一万字**（备份救回）。
   静默兜底 + 形状假设，是这类数据丢失最常见的组合。
2. **url 字段回读是 Markdown `[text](href)`，写入却是裸串。** 不归一化的后果不是显示错，
   是**每轮都判定"变了"→ 无限重复回写**，「最后同步」被刷成噪音，反而看不出哪行真动过。

修完两处幂等都成立：pull 连跑两次字节相同、push 第二次 0 行。
