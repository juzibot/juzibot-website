Claude 5 时代模型上下文工程的新规则

我们为更先进的模型移除了 Claude Code 超过 80% 的系统提示。如何将我们学到的经验应用到您自己的 Claude Code 上下文工程以及您自己构建的智能体中。

我之前写过关于如何最好地 提示最新的 Claude 5 模型 并通过迭代方式与它们协作，以发现您想要构建的内容。

但是，当您向 Claude 发送消息时，提示只是它所获取上下文的一小部分。您的上下文大部分是由系统提示、技能、CLAUDE.md 文件、记忆和其他来源组合而成的。我们称之为 上下文工程，它在使用 Claude Code 或构建您自己的智能体时，对您生成结果的影响巨大。

与提示不同，上下文通常在许多请求中重复使用，因此它不能过于具体。您如何为 Claude 构建这些通用的提示和指导，特别是当您不知道用户的提示可能是什么的时候？

随着 Claude 自身能力的不断进化，这可能出人意料地困难。最近，我们注意到在提示最新一代 Claude 模型的方式上有了巨大飞跃。对于 Claude Opus 5 和 Claude Fable 5 等模型，我们移除了 Claude Code 超过 80% 的系统提示，但在我们的代码评估中并未发现任何可衡量的性能损失。

以下是我们关于提示这类新模型的经验，以及您如何利用它来更新您的上下文工程。我们将这些最佳实践放到了 `claude doctor;` 命令中，在 Claude Code 中使用 /doctor 命令来调整您的技能和 CLAUDE.md 文件。

为 Claude 松绑

总体而言，我们发现我们通过系统提示以及 CLAUDE.md 文件和技能对 Claude Code 的限制过多。

例如，当我们阅读 Claude Code 内部使用记录的文本时，会发现单个请求中存在多条相互矛盾的信息，比如“适当添加文档”或“不要添加注释”，因为我们的系统提示、技能和用户请求之间发生了冲突。

通常，Claude 能够理解用户的意图以给出正确答案，但在决定做什么之前，Claude 必须更仔细地思考这些重叠和矛盾的信息。

虽然这些约束曾经是为了避免最坏情况而必需的，但我们后来发现可以删除其中很多约束，让模型使用上下文和判断力来替代。

此外，Claude Code 现在有了更多工具。过去 Claude 依赖 CLAUDE.md 作为记忆、信息和指导的来源。现在我们有记忆、工件和技能，Claude 可以利用它们来创建在会话间加载和共享上下文的新方法。

过去与现在

过去有一些上下文工程的最佳实践已经变成了误区，包括：

过去：给 Claude 制定规则

现在：让 Claude 使用判断力

当我们首次推出 Claude Code 时，我们需要确保 Claude 避免最坏情况，比如删除文件。这意味着我们会给出特别强烈的指导，而这些指导并不总是正确的。例如，在系统提示中我们过去会说：

在代码中：默认不写注释。永远不要写多段文档字符串或多行注释块——最多一行短注释。除非用户要求，否则不要创建计划、决策或分析文档——根据对话上下文工作，而不是根据中间文件。

但对于某些特定提示，这种指导可能是错误的。在文档编写的情况下，用户可能有自己偏好，或者非常复杂的代码的某些部分可能需要多行注释块。

尽管如此，在没有这些护栏的老模型中，Claude 写的注释在很多情况下都是不正确的，我们不得不接受这种权衡。但新模型有更好的判断力，可以在没有明确规则的情况下很好地处理这些决策。

在新系统提示中我们说：编写与周围代码风格一致的代码：匹配其注释密度、命名习惯和惯用写法。

过去：给 Claude 示例

现在：设计接口

工具使用的第一条规则是给 Claude 示例，教他们如何使用工具。在我们最新的模型中，我们发现给示例实际上会限制它们在特定探索空间内的发挥。

与其使用示例，不如更多地思考你的工具、脚本和文件的设计——Claude 有哪些参数，如何让它们更具表现力？

例如，在 Todo 工具示例中，仅将状态列为待处理、进行中和已完成之间的枚举，就暗示了 Claude 如何使用它。关于保持一项任务处于进行中的指令，有助于定义我们期望的行为。

过去：把所有内容都放在前面

现在：使用渐进式披露

由于 Claude Code 专注于编程，我们的系统提示包含了关于如何进行代码审查和验证的详细信息。这些信息并非总是需要，但当需要时，就是关键信息。

从那时起，Claude Code 已经非常擅长使用渐进式披露——在合适的时候加载合适的上下文。例如，我们将验证和代码审查移到了它们自己的技能中，Claude Code 可以选择性调用。

但渐进式披露不仅适用于技能，也适用于工具。我们的一些工具是“延迟加载”的，这意味着代理在使用它们之前必须通过 ToolSearch 搜索其完整定义。这让我们可以拥有更多工具（例如我们的 Task 工具），这些工具在不需要时不会占用上下文。

同样的方法也可以应用于你自己的 CLAUDE.md 和 Skill.md 文件。一个常见的误解是，你应该把这些文件做成你可能遇到的每项实践的中心知识库，因为 Claude 否则找不到它们。相反，考虑使用一个可以在适当时机加载的文件树。

过去：重复说明

现在：简洁的工具描述

早期的 Claude 模型有时需要重复的指令，或者更倾向于关注上下文窗口末尾的指令，而不是开头的指令。这意味着我们的系统提示中有时会在主系统提示中引用工具，同时在工具描述中也包含相关说明。

我们发现可以删除这些重复的示例，并将工具使用说明直接放在工具描述中，而不是系统提示里。

过去：CLAUDE.md 文件中的记忆

现在：自动记忆

过去我们鼓励用户通过使用 # 快捷键将内容自动写入到他们的 CLAUDE.md 文件来保存信息。现在，Claude 会自动保存与您工作相关且对您重要的记忆。

过去：简单的规范说明

现在：丰富的参考资料

在规划模式下，Claude Code 严重依赖包含计划的 markdown 文件。将这些文件作为计划存储，有助于 Claude 在需要时参考它们。另一个类似的最佳实践是在代码库中存储规范说明，供 Claude 在处理长期项目时参考。

但我们发现 Claude 能够处理越来越复杂的参考资料。除了简单的 markdown 文件，Claude 还可以引用我们新功能生成的制品（artifacts）所创建的 HTML 文件。

您也可以以代码的形式给 Claude 提供参考资料。规范说明也可以是一份详细的测试套件，或者是 Claude 可能需要移植到其他代码库中的函数。

评分标准（Rubrics）是另一种形式的参考资料。评分标准允许 Claude 通过使用 动态工作流 和基于这些评分标准启动验证代理（verifier agents）的方式，来尝试并验证您在特定领域的品味（例如，一个好的 API 设计应该是什么样的）。

将此应用到您的上下文中

综合来看，当您组装自己的上下文时，这会是什么样子呢？

系统提示

系统提示与产品上下文紧密相关。它告诉 Claude 它正在操作什么产品以及正在做什么。对于 Claude Code，您可能永远不会修改这个部分，但如果您正在构建自己的代理框架（agent harness），这就是您应该投入大量时间的地方。

CLAUDE.md

让你的 CLAUDE.md 保持简洁，简要说明你的仓库是做什么的，但把大部分篇幅留给代码库中的注意事项。例如，你可以将代码组织成将所有类型放在一个单独的大文件中，其他地方不放。避免陈述那些 Claude 通过查看你的文件系统或仓库就能知道的“显而易见”的事情。

大量使用渐进式披露，例如，如果你有多个验证工作的独特指令，可以创建一个验证技能并在你的 CLAUDE.md 中引用它。

技能

将技能视为轻量级的指南，让 Claude 在需要时能找到信息。除了在极其重要的领域，避免让技能过于受限。

对于较长的技能，应尽可能多地使用渐进式披露——将其分成多个文件并拆分开来。

最好的技能是能编码出属于你、你的团队或产品的特定观点、知识或最佳实践。

引用 

你可以 @ 提及文件将它们作为引用。引用能让 Claude 参考当前计划的详细信息。

这些信息可能在规范文件、模型图，甚至是整个代码库中。通常你应该优先选择代码中的文件，因为它为 Claude 提供了清晰、高保真的指令，而 Claude 非常熟悉这种语言。例如，一个设计的 HTML 模型图通常比设计的描述或截图能产生更好的效果。

尝试简化

在你的系统提示、技能和 CLAUDE.md 文件中，你可能也需要像我们一样进行简化。我们推出一个名为 `claude doctor` 的新命令，它也能帮助你自动完成这项工作。有关针对更高级模型进行提示的更多详细信息，请查看我们的 Fable 实践指南。
