大约六年前，我们发表了一篇关于 IDE 的文章，核心观点是 IDE 变得如此强大和功能丰富，以至于还有人像原始人一样使用 Vim 或 Emacs，这简直令人难以置信。虽然这篇文章确实有些挑衅性，但它确实激怒了很多开发者。评论来自双方，既有批评文章不理解开发者工作方式的人，也有整天宣扬 Emacs 优越性的开发者。但大多数时候，大家进行了很好的讨论，探讨这些工具为什么实际上很有用。

对于新手来说，Vim 和 Emacs 可能看起来是一些不直观的终端程序，需要记住神秘的快捷键才能使用（以及 退出）。但对于经验丰富的用户来说，使用它们可以像思考一样自然。有一条评论提到了 David Thomas 和 Andrew Hunt 合著的 The Pragmatic Programmer，书中解释说开发者——他们是（或曾经是）工匠——需要“锋利的工具”，这些工具应该像他们手的延伸一样。Vim 和 Emacs 凭借其无限的定制能力，可以被塑造成完全符合你的手型和工作流程。花时间建立对工具的熟练度和信任，并对其进行改造以适应自己，会带来巨大的回报。

在这个智能工程时代，新工具是你可以用自然语言对话的终端。编程代理缺乏开发者编写精心设计的代码时的精确性和专业性，但它可以在一小部分时间内输出完整的应用程序。至今仍在回响的问题是，这些输出是否值得信赖。我们最新的开发者调查发现，开发者使用 AI 越多，对它的信任度就越低——使用率从 76% 上升到 84%，但信任度却从 40% 下降到 29%。

工具本身是新的，它们的能力也在不断变化。如果你的厨房刀不断改变形状、重量和刀刃，你每次都得重新学习它；这是一个很难建立信任的工具。但这也指出了你使用该工具、围绕它的流程以及工具如何强化流程的方式中存在缺陷。你信任你最喜欢的刀、IDE、画笔或其他任何东西，都是因为你与它建立了信任，以及围绕它的流程。

在本文中，我们将探讨工具如何构建可信赖的流程，工具变更如何凸显但无法修复已破损的流程，以及工具与文化如何协同工作来建立新的信任。

工具是流程的一部分

开发者工具随着软件开发整体而运作和演进，同时也与个别开发者共同成长。如果你从终端开始工作和学习——或许是在 IDE 或图形界面尚不存在的年代——那么你理解代码创建的方式就包含了这些终端和终端文本编辑器。加入 IDE 不仅需要学习新工具，还需要重构你的代码编写流程。

如果从终端迁移到 IDE 是一个艰难的流程转变（或者说，如某些人所说，是没必要的），那么从终端或 IDE 迁移到智能编程工具则更加困难。“我之所以对拥抱某些 AI 编程工具有所保留，是因为我用 IDE 更快，因为我熟悉它的运作方式，”开发者生产力倡导者 Tricia Gee 表示。“当我与那些非常熟悉 Vim 和 Emacs 的人共事时，我也见过同样的情况。你可以使用 IntelliJ IDEA 中的重构工具。他们会说，是的，但这需要学习曲线。我已经用了这么久的工具，我的手指知道该做什么。无论是什么工具，只要非常熟悉它，就会形成大量的无意识能力。”

培养这种肌肉记忆，这种关于软件在代码层面如何运作的隐性知识，让开发者能够信任他们的工具来帮助生成和改进代码。与此同时，AI 智能体更快、更不透明、更不可预测。你使用模糊的语言来创建软件，而不是代码。“代码是对解决方案的精确陈述，”C++ 创造者 Bjarne Stoustrup 说。“英语是一种糟糕的语言，无法表达必须明确无误的事物。”一个值得信赖的工具是可预测、可靠的。你不需要反复使用 Emacs 或 Vim 进行迭代。

大多数开发者工具，比如 IDE、容器化工具或静态分析工具，你都知道它们的边界在哪里。它们各司其职，不会越界。但 AI 正在渗透到 SDLC 工具链的各个环节。这意味着 开发者对 AI 的信任度降低 的问题会影响到整个流程。代码生成可能更快了，但验证代码、让它达到开发者可以信任不会导致昂贵生产故障的程度，往往需要更长的时间。

工具能固化流程，但无法修复流程

智能编程工具改变了软件开发过程的本质。围绕旧流程产生的那些工具——代码检查器、自动化单元测试、CI/CD 等——以现有形式可能不再适用于这个改变了的流程。

那些工具固化了流程，但它们并非流程本身。一个优秀的 CI/CD 工具并不意味着你能更快地发布产品。一个优秀的 IDE 并不意味着你能写出更好的代码。一个带有故事点的缺陷跟踪系统也不意味着你能很好地估算工作量。流程的某些部分存在于文化中，存在于构建软件的人员的行为和规范里。新工具往往意味着 改变组织文化。

在任何大型工程组织中工作的人都会对这个故事感到熟悉。无论新工具有多大的潜力，如果不能融入现有的文化和流程，就可能失败。成功的工具需要以开发者能够接受和理解的方式去改变文化和流程。你们都喜欢构建事物和解决问题，所以那些不能帮助你们更好地做到这一点的工具会被忽视。

智能编程之所以能被迅速采用，是因为它让开发者能更快地解决问题。但当代码生成变得轻而易举时，它也暴露了现有流程中的许多缺陷。一直以来，需求不明确且频繁变动都是一个难题，但现在解决问题需要精确定义“问题”和“解决”这两个词的含义。

代码可能（几乎）是免费的，但验证它可不是。新的瓶颈变成了代码审查。老笑话是说，如果你想快速通过 PR，就改 100 行代码。编程代理能瞬间修改数百行代码，然后把巨大的差异文件发给人类审查（或直接放行）。LLM-as-a-judge 正在演变成一种可扩展的解决方案，但要建立一种能信任 AI 审查 AI 写的代码的工程方法，还需要付出努力。

同样，运行代码也不是免费的。你有基础设施的成本，在云原生时代，这取决于你的应用程序所消耗的计算、内存和流量。你有托管依赖项和 API 的成本。还有故障的成本，这是最难预算的部分：停机时间、安全漏洞和机会成本。那些生成的软件无法（或不会）考虑这些成本的工具可能并不值得。它们还会给你建立的、曾经能产出可靠可信软件的流程带来压力。

对许多人来说，由于代理编程，软件开发生命周期（SDLC）开始看起来已经支离破碎了。自然，这些人正在寻找新工具来修复这些裂缝：AI SRE、自动化代码审查、内存和上下文管理器、控制平面和工具链改进等等。这些都是 AI 驱动的软件组织中工具的坚实补充。但仅靠工具无法解决问题，特别是如果文化和流程保持不变的话。一个糟糕的流程配上更好的工具（人们可能还不会用）依然是糟糕的。

通过更好的流程建立信任

在传统的 SDLC 中，产品经理会根据他们的研究、客户对话和对竞争对手的了解，提出功能和特性需求。架构师会根据他们多年的经验和对现有技术栈的理解，来规划软件。工程师会根据他们对代码逻辑和现有代码库的知识来构建代码并审查提交。QA 会根据他们对软件如何出错的审查和测试经验，来审查并试图搞垮软件。一旦软件部署到生产环境，DevOps 和 SRE 就会根据他们以往的经验来监控和管理性能和资源使用情况。

你通过与人合作、理解他们的思维方式，并限制任何个人或工具可能失控并破坏系统的途径，来建立对这个系统的信任。在人工智能赋能的软件开发生命周期（SDLC）中建立信任也需要同样的东西：与人合作并确保他们有责任心和担当，分享工作流程并持续改进，同时最大限度地减少出错的可能性。

第一步是确保我们将人类确立为责任主体，并标明人工智能的贡献所在。人人都谈论“人在回路中”（human-in-the-loop），但正如 Honeycomb 的首席技术官 Charity Majors 指出的那样：“‘人在回路中’听起来就像是一种怜悯的邀请。我创造了这个回路，我拥有这个回路，我是这个回路存在的唯一原因。这他妈的就是我的回路！”推动提交代码的人拥有那段代码。批准那些拉取请求（PR）的人拥有那份批准。如果在人工智能出现前，你在周五搞砸了生产环境，你不会责怪你的集成开发环境（IDE）。如果你现在搞砸了，问题不在于那个代理（agent），而在于键盘和椅子之间。

在人工智能时代，协作可能变得更加困难和陌生。代理（agents）让你可以扩展“全栈开发者”的概念，让一个编码代理就能处理从产品需求到 DevOps 的所有事情。开发者很容易就会变成一个孤立的个体。Slack 的首席产品官 Jaime DeLanghe 说：“你不必，比如说，和你的设计师确认设计方案，因为你直接让代理生成了设计；你也不必为了理解某个特定领域的代码库而去和另一位工程师合作，因为你直接问代理就行了。你可能会在这条路上越走越远，最终生成一个巨大的拉取请求。”

一些人建议在共享空间中提示代理，这样每个人都可以评论和修改流程。另一些人则建议每个 PR 都应包含提示过程的记录。这种与代理的对话视图甚至能让我们更深入地了解那段代码是如何诞生的。“能够打开一个 PR，真正看到开发者的思路以及他们是如何解决问题的，这太酷了，”Dane Knecht 说道，他是 Cloudflare 的首席技术官。

旧流程通过访问控制、审计跟踪、差异比对以及 CI/CD 检查来限制任何错误的波及范围，而新流程则需要在代码编写前就消除不确定性。这意味着你必须确保所有希望代码实现的功能都在提示中明确说明。你可以为此使用 spec.md 文件，但任何未被指定的内容现在都有可能被构建出来。“如果你把任何事交给运气，那结果就只能听天由命了，”Scott Hanselman 说道，他是微软开发者社区副总裁。“我需要开发一个小型的环形灯应用，我的系统是 x64 架构。但我希望它能在 ARM 上运行，所以我必须告诉它：‘给我做一个 ARM 版本。’如果我不说，它就不会发生。”

当然，你不可能把所有需要的东西都塞进一个巧妙的提示里（也不应该这么做）。那样做会导致大量重复，而且几乎肯定会遗漏一些作为公司隐性知识存在的事项。现在有很多聪明的人正在思考如何为你的代理提供更好的上下文，以及赋予它们长期和短期记忆。关键在于为你的代理提供代码所需的正确上下文。通常，这些是资深开发者随时间积累的经验。但代理需要你将这些知识记录在某个地方（比如 Stack Internal），验证它，并在需要时将正确的部分作为上下文提供给代理。

所以你拥有了世界上最棒的提示词。你给代理提供了正确的上下文，它构建的东西通过了同行评审并成功部署到生产环境。接下来，你要确保永远不要再开发这个功能。你已经有了一个完美的软件组件，别浪费它，复用它吧。“DRY（不要重复自己）原则是我们的核心原则，”Laly Bar-Ilan（Bit公司首席科学家）说。“如今的AI本质上就是WET（什么都写两遍）。这个开发者告诉它‘生成一个按钮’，它就照做了，然后另一个团队的开发者也来问它，结果代码库里又多了一个按钮。”

不过，与AI代理建立信任的最大技巧，或许在于知道什么时候不该使用它们。即使你在流程中设置了上述所有防护措施，但由于AI的本质，其中仍存在一定的随机性。如果你已经有了一个很好的非确定性解决方案，何必重复造轮子呢？“我们试图在很多本该使用确定性代码的场景中应用非确定性系统，”Anil Dash说。“大语言模型不擅长这个，那我们为什么要把它们当作锤子，去敲那些根本不是钉子的东西呢？那个已经稳定运行了六年的bash脚本就很好。”

过去，我们通过合作的人和工具建立信任。这种信任源于可预测性：你知道他们能做什么，了解他们的优缺点，并且你周一和他们的合作体验，周二也能保持一致。AI的概率特性，加上改进和变化的速度，彻底打破了这一切。流程改进可以帮助工程师重新建立开发中的信任。

结论

在美好的旧时光里，我们围绕人建立流程，并且信任这些流程，因为我们信任共事的人。我们构建了信任的工具来管理流程，这些工具成为了我们自己和共事者的延伸。

借助AI，我们能够自动化许多这些流程。好消息是工作完成得更快了。坏消息是完成后我们不信任它。工具是新的，人们正在转向更高层次的角色，我们仍然需要建立信任。通过一个更深思熟虑、明确定义的工作流程，保留人类的判断力，我们就可以开始在新系统中建立信任。

成功的团队不会是那些产出最多代码的团队。他们会是那些构建反馈循环、提供最佳背景知识的黄金标准知识，以及将你的流程与工作流程对齐的工具的团队。
