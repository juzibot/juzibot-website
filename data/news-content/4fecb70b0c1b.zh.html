这个故事太离谱了。简单来说：OpenAI 正在对一个未发布的模型进行网络安全测试，但关闭了该模型的安全防护功能。结果模型没有解决测试，反而冲破了 OpenAI 的沙盒环境，然后找到了漏洞入侵了 Hugging Face，目的就是为了偷取答案来作弊。

整个过程也让我们看到了一个最有力的证据：模型获取的不平衡正在损害我们保障软件安全的能力。

事情是这样的

目前我们有三份文件可以帮助我们了解发生了什么。

  1. ExploitGym：AI 能否将安全漏洞转化为真实攻击？ 是一篇于 2026 年 5 月 11 日发布的论文，描述了 ExploitGym——一个用于评估大语言模型驱动系统的新评测套件。
  2. 安全事件披露 — 2026 年 7 月 由 Hugging Face 于 2026 年 7 月 16 日发布，描述了他们如何检测到来自一个“智能型安全研究工具——使用的 LLM 仍未知”的攻击，该攻击侵入了他们的一些系统。
  3. OpenAI 与 Hugging Face 合作处理模型评估期间的安全事件 由 OpenAI 于 2026 年 7 月 21 日发布，承认这次攻击是 他们 的智能工具造成的，并且他们正在与 Hugging Face 一起处理后续问题。

ExploitGym

我之前没看过 ExploitGym 的论文，但内容确实非常有趣。加州大学伯克利分校、马克斯·普朗克研究所、加州大学圣塔芭芭拉分校和亚利桑那州立大学的研究人员设计了一个新的基准，用于评估模型将已知漏洞转化为具体攻击的能力。OpenAI、Anthropic 和 Google 提供了反馈，并协助用他们的模型运行了该基准测试。

该基准“包含 898 个源自真实世界漏洞的实例，这些漏洞影响了流行的软件项目”——包括 Linux 内核和 V8 JavaScript 引擎。ExploitGym 基准测试可在 GitHub 上获取。

下面最能代表他们基准测试结果的段落是：

在所有配置中，Claude Mythos Preview 和 GPT-5.5 取得了最高的成功次数（分别为 157 次和 120 次），这表明当前最前沿的智能体在受控条件下能够利用大量真实世界漏洞。GPT-5.4 也成功解决了 54 个任务，处于一个中等水平。其余的模型-智能体组合每个解决的任务都少于 15 个，这凸显了端到端的漏洞利用仍然具有挑战性，并且与当今最前沿的系统形成了鲜明对比。值得注意的是，尽管 Claude Opus 4.7 是一个更新的模型版本，但其成功次数却少于 Claude Opus 4.6，并且在完整测试集上的成本也显著降低。通过检查执行轨迹可以发现，Claude Opus 4.7 和 Gemini 3.1 Pro 经常在判断目标漏洞不可利用后提前终止任务。

论文还描述了他们所采取的方法，以防止智能体通过超出测试参数范围的方式进行作弊。这一点接下来就会变得很重要！

出站连接被限制在一个精心筛选的允许列表中，该列表允许常规的软件包安装（Ubuntu apt 仓库和 PyPI）以及获取构建 V8 所需的工具链。所有其他外部端点都被阻止。

论文的结论如下（强调部分为我所加）：

我们的结果表明，前沿 AI 智能体自主开发漏洞利用程序已不再是假设性的能力。尽管当前的智能体还不能在所有目标上保持可靠，但它们已经能够利用大量真实世界的漏洞，包括内核组件等复杂目标。这种能力的快速出现本身就是一项核心发现，它表明那些曾经看似不可能实现的能力，现在已经存在于已部署的前沿模型中。

这里有一个重要细节：这篇论文并非关于漏洞的发现，而是关于如何利用这些漏洞并将其转化为可用的漏洞利用程序。

当 Anthropic 在 今年四月首次限制 Mythos 的访问权限时，他们也提到了这种能力。一个能够利用漏洞的模型，比仅仅能发现漏洞的模型要危险得多。

Fable 与 Mythos 的一个不同之处在于，Fable 更有可能拒绝以这种方式将漏洞武器化。我得到的印象是，美国政府在 上个月禁止 Fable 时，并没有理解这一区别。

Hugging Face 事件

我们首次得知这次攻击是在2026年7月16日这篇Hugging Face的博客文章中：

一个恶意数据集利用了我们数据处理流程中的两个代码执行路径（远程代码数据加载器和数据配置中的模板注入），在处理工作节点上运行了代码。攻击者借此获得了节点级访问权限，窃取了云和集群凭证，并在一个周末内横向移动到多个内部集群。

我希望他们能公布更多关于实现这次攻击的代码细节。我猜测这指的是使用了datasets库的包，这是Hugging Face的一个用于在其平台上打包和共享数据集的项目。该库曾经可以执行任意代码，但随着时间推移已被逐步收紧，在2025年7月的4.0.0版本中完全移除了trust_remote_code=True标志。

假设攻击者使用了那个库，那么他们要么以某种方式滥用了pickle序列化，找到了其他不明显的代码执行路径，或者（最有可能的是）将依赖项指定为datasets<4.0.0。

这次攻击是由一个自主代理框架（似乎基于一个代理式安全研究工具链——使用的LLM尚不明确）执行的，该框架在大量短暂的沙箱中执行了数万个独立操作，并将自迁移的指挥与控制部署在公共服务上。

这是一次非常复杂的攻击！

然后Hugging Face遇到了障碍：他们试图使用"商业API背后的前沿模型"——我猜来自Anthropic和OpenAI——来帮助分析攻击，但被阻止了：

当我们开始日志分析时，我们首先使用了商业API背后的前沿模型。但这行不通：分析需要提交大量真实的攻击命令、利用载荷和C2（指挥与控制）工件，而这些请求被提供商的安全护栏阻止了，这些护栏无法区分事件响应者和攻击者。

他们切换到了自己托管的、采用MIT许可证的GLM-5.2实例，这帮助他们弄清了发生了什么。

这表明防御团队和（至今仍不为人知的）攻击者之间存在一种根本性的不对称：

我们不知道攻击者的代理使用的是哪个模型，无论是越狱的托管模型还是无限制的开源权重模型；无论哪种情况，攻击者都不受任何使用政策的约束，而我们自己的取证工作却被我们最初尝试的托管模型的安全护栏所阻碍。

作为一个有用的指标，表明他们对这次攻击的重视程度：

[...] 最后，我们也已向执法机构报告了这一事件。

那么，这个“自主代理框架”的负责人是谁呢？结果竟是 OpenAI 自己。

OpenAI 的坦白

五天后，在7月21日，OpenAI 揭露了罪魁祸首。他们当时正在对一个全新的、尚未公开的模型运行 ExploitGym 基准测试，而该模型的运行方式 远远 超出了其预期参数（强调部分为我所加）：

经过调查，我们现在知道这起特定事件是由一系列 OpenAI 模型共同驱动的——包括 GPT‑5.6 Sol 和一个能力更强的预发布模型，所有模型都为了评估目的而降低了网络拒绝响应——同时，这些模型正在一个基准测试⁠[ExploitGym]（用于评估网络攻击能力）的内部测试中运行。[...]

我们通过在运行评估时移除那些用于阻止模型从事高风险网络活动的生产级分类器，来评估其最大网络攻击能力。我们的基准测试在一个高度隔离的环境中运行，网络访问权限被限制为只能通过一个内部托管的第三方软件来安装包，该软件充当包注册表的代理和缓存。

这些模型识别并利用了 OpenAI 研究环境和 Hugging Face 生产基础设施中的漏洞，直接从 Hugging Face 的生产数据库中获取测试解决方案。所有证据都表明，这些模型极度专注于为 ExploitGym 寻找解决方案，为了实现这个相当狭隘的测试目标，不惜采取极端手段。

事情的经过已经很清楚了。OpenAI 为一个正在开发中的模型移除了安全过滤器，将其锁定在一个沙箱里，并让它去解决 ExploitGym 的问题。由于缺乏安全护栏，没有任何东西能阻止该模型尝试突破沙箱、入侵 Hugging Face，并从那里直接读取答案。

OpenAI 的沙箱采用了现在常见的模式，即通过一个受控的代理，允许访问一个与安装额外软件包相关的网站白名单。用 OpenAI 的话来说：

在我们的沙盒测试环境中运行时，我们的模型花费了大量推理计算资源来寻找获取开放互联网访问的方法，旨在解决评估问题。为了获得访问权限，模型识别并利用了软件包注册表缓存代理中的一个零日漏洞（我们已负责任地向供应商披露了该漏洞）。通过这个访问权限，我们的模型在研究测试环境中执行了一系列权限提升和横向移动操作，直到模型到达一个具有互联网访问权限的节点。

所以第一步是突破到公共互联网上。然后模型入侵了 Hugging Face 来寻找答案：

获得互联网访问权限后，模型推断出 Hugging Face 可能托管了用于 ExploitGym 的模型、数据集和解决方案。了解到这一点后，模型搜索并成功找到了获取机密信息的方法，这些信息可以用来欺骗评估。在一个例子中，模型将多个攻击向量串联起来，包括使用窃取的凭据和零日漏洞，在 Hugging Face 服务器上找到了一个远程代码执行路径。

将多个攻击向量串联起来，正是这些新模型能够做到的事情，而以前的模型版本可能做不到这一点。

我上个月写过关于Claude Fable 如何不知疲倦地主动出击的文章，当时我注意到它在我的笔记本电脑上启动自定义 Web 服务器并部署 CORS 技巧，只是为了帮助调试一个 WebKit CSS 问题。事实证明，不知疲倦的主动性是这一代 Mythos 级模型的决定性特征。如果你为它们设定一个目标，并且（哪怕是无意中）给了它们实现目标的方法，它们一定会找到办法。

别把这当成噱头一笑而过

肯定会有人把这件事当作 OpenAI 的不诚实营销手段，目的是让他们的模型听起来可怕地有效。我在该事件的 Hacker News 讨论中找到了 81 个"营销"这个词的实例。

对这些人，我想说别再自欺欺人了——你们现在把 Hugging Face 也纳入了阴谋论，只是为了否认这里越来越多的证据！

我们目前最先进的模型已经具备了发现并利用新漏洞的能力。《ExploitGym》这篇论文的结论也指出，“前沿AI代理自主开发攻击手段已不再是假设性的能力”，而这次事件正是这一点的完美例证。

这种不对称性正变得越来越令人沮丧

这个故事中最令人恼火的细节之一是，当 Hugging Face 面临来自 OpenAI 模型的一次意外且猛烈的攻击时，他们却无法反过来利用 OpenAI 的模型来帮助他们抵御这次攻击。

我们能够接触到的前沿模型在帮助我们保护软件方面的能力正受到越来越多的限制，这很大程度上受到了美国政府持续不断的出口管制威胁的影响。Claude Fable 5 甚至不肯 为我校对这篇文章！它坚持要把我降级到一个能力较弱的模型。

与此同时，来自中国的开源模型，如 GLM-5.2、Kimi 3 和新的 Qwen 3.8 Max，似乎没有任何此类限制——而任何确实存在的限制，都可能通过修改权重来微调掉。

这些限制的初衷是为了让我们更安全。但我认为，它们反而可能带来相反的风险。
