更新（2026年7月29日）： 我们使用相同的配置运行了 Kimi K3，并通过 SGLang提供服务。K3 的权重为 1.4TB，无法放入用于 GLM-5.2 的 8×B200 节点的内存预算中（1.5TB 的总 HBM 内存没有 KV 缓存的余量）。因此这次运行使用了 8×B300 节点，每块 GPU 拥有 288GB HBM 内存，而不是 192GB，即每节点 2.3TB。与 8×B200 配置相比，这平均高出约 20% 的硬件成本，具体取决于您的租赁服务商。

在我们的测试中，K3 支持 16 个并发会话（GLM-5.2 支持 24 个）。总体 token 吞吐量低约 30%（16 用户时为 122 vs 170 tok/s），中位任务时间长约 50%（38 vs 26 分钟）。这使得 K3 比我们的 Claude Code 基准测试慢约 8 倍。然而，K3 在质量上弥补了这一差距，解决了 86.4% 的任务，比 GLM-5.2 和 Opus 4.8（两者均为 62.5%）高出 24 个百分点。需要注意的是，我们来自 SWEBench Pro 的基准测试任务可能已在 K3 的训练数据中，因此请对该解决率持保留态度。本文中只有图表更新了新的 K3 数据。

01

为什么你今年的 token 账单
爆炸式增长

今年初的警告信号无处不在：GitHub Copilot 切换为基于 token 的计费 [1]，Uber 仅用四个月就耗尽了年度 AI 工具预算 [2][3]，开发者报告称预计成本从每月 29 美元跃升至 750 美元 [4]。我们甚至为此创造了新词："tokenmaxxing"、"token 恐慌"、"token 预算"。

普通员工 [5] 目前每年在 AI API 使用上花费约 140 美元。听起来无害，直到你看看尾部数据：第 90 百分位接近每年 7,300 美元，第 99 百分位接近 90,000 美元。对于许多组织来说，智能体 AI 的采用才刚刚开始，因此预计这些数字在未来一年内会发生变化。

为什么账单如此不稳定？因为我们使用 AI 智能体的方式：目前，主要模型提供商 [4] 的 ARR（年度经常性收入）中，超过 70% 来自编程用例。你交给智能体的工作流程越多，你的 token 账单就越高。

许多组织开始采用 AI 编程智能体时，是通过 API 访问 OpenAI 或 Anthropic 等主要前沿模型提供商。几个月后，越来越多的组织出于多种原因至少开始考虑替代方案：token 定价模型变得更加昂贵，用户正在升级到更新、更昂贵的 AI 模型，并且组织内的智能体采用开始激增。存在一些明智的替代方案，绝对值得仔细考虑：切换到 API 路由器；为日常工作使用更便宜的模型层级，仅将困难的 20% 升级到前沿模型，等等。

然而，如果你的令牌消耗量变得很大，或者你正在处理敏感数据，你可能需要完全放弃 API 方案，转而搭建自己的推理栈。当硬件所有权成为问题时，你需要弄清楚租用或拥有 GPU 到底能给你带来什么回报。什么时候做这个切换才合理？继续阅读，我们会给你工具让你自己做出决定。

02

你为整个资源池 24/7 付费，
而你的团队每天只使用 8 小时

所以你决定研究一下购买或租用自己的 GPU 是否合理。一旦正确配置，它会给你一个 API 端点，你可以将其接入到你的编码工具中，就像 Anthropic、OpenAI 或其他模型提供商提供的那样。

与前沿 API 不同，你自己的端点在每秒输出令牌数上有上限，但只有当系统完全负载时才会达到这个上限。一个开发者单独工作会留下大部分未使用的上限，但同一硬件同时为四十八个代理会话服务就是另一回事了。你的上限由模型、GPU 和服务配置决定。

与按消耗的令牌计费的 API 使用模式不同，运行你自己的设施意味着你要为基础设施及其运行成本付费。在极少数情况下，这意味着即使你没有在生成令牌时，你也在为它付费。这种权衡是否适合你，取决于两个问题。第一个问题是你的资源池利用率有多高。我们先来解决这个问题。

你为峰值需求配置资源，并为此 24/7 付费。决定成本效益的是利用率，而不是员工人数。

真实的需求并非恒定不变，而是呈尖峰状。对许多组织而言，用于编码任务的 token 消耗量可能在夜间降至接近零，然后在上午逐步攀升，午餐时段明显下降，并在下午再次达到峰值。这意味着你为 峰值 负载购买硬件，却需要 24/7 全天候付费（除非你租用“GPU 现货实例”，但在这种情况下更难依赖）。使用峰值的形状与峰值量同样重要：单一时区的团队会将 token 需求集中在更狭窄的尖峰上，而同样人数分布在多个时区的团队则情况不同：消耗相同的 token，峰值更高，但持续时间更长。关于为企业内部开发者工具提供推理工作负载的公开数据显示，平均 GPU 利用率仅为 15–22% [6][7]，尽管即使是目前运行良好的部署也很少超过 25–35%（这已经是相当乐观的估计）。下图来自我们的朋友 TechWolf[14]，展示了几天前真实的 token 使用情况，准确反映了我们上述描述的现象。

这里有一个新兴的趋势可能对你有利：随着组织在基于智能体（agent）的工作流程上日趋成熟，越来越多的会话开始来自自动化智能体而非人工操作（如定时任务、智能体在凌晨 3 点自动处理错误报告等）。这使得工作不再局限于办公时间。如果能有意识地安排这些自动化会话，它们就能充分利用你本已付费的夜间闲置容量。

现在我们来探讨第二个问题，在性能开始变慢之前，多少开发者可以共享这个资源池？

03

当
48 个开发者共享一台服务器时会发生什么？

仅由一名开发者使用的 token 资源池体验极佳——token 的流入速度快到你根本读不过来。问题在于，当有五、十或二十个并发开发者会话时会发生什么，因为 AI 编码智能体是贪婪且突发的客户端，它们不仅消耗 token，还会浏览网页、执行文件或编译代码。

当你不再使用前沿模型提供商的 API 时，主要关注点之一应该是开发者体验。查看基准测试结果时，你经常会看到使用 token/秒来衡量模型在特定 GPU 配置下的性能表现。虽然这是一个易于理解的指标，但我们发现它在当前场景下用处不大。毕竟，你可能消耗了数千个 token 却没有得到任何可用的结果，或者切换到一个更小的模型，结果反而使用了多 10 倍的 token。

价值交付的更好单位是成功完成的任务，虽然这在通常情况下更难量化，但这正是我们在下文分析中会反复探讨的核心。你需要理解一个任务从开始到结束需要多长时间以及当代理等待模型时，token的流速能有多快。

价值交付的更好单位是成功完成的任务。

为了让任务完成度可衡量，我们使用了来自 ScaleLabs 的 SWEBench Pro 中的一组任务子集，这是一组流行的长期代码工程任务。虽然它最常被用于让各个模型相互竞争，但我们的团队专门用它来创建一个更逼真且具有足够挑战性的工作负载，以便我们在实际使用场景中比较不同模型和硬件组合的成本与性能，这些场景对您的组织来说是合理的。

通过几张图表，我们可以进一步评估我们选择的模型和硬件组合的性能。首先，我们在不断增加的用户并发级别下，使用特定硬件配置上的给定模型运行我们的代码任务子集，并评估这如何影响单个任务的完成时间。这将帮助我们找到那个最佳平衡点：在您选择的配置下，可以有多少并发用户同时活跃，而任务不会因为耗时过长而无法完成。

将这些信息放在一起看会非常直观。通常，硬件使用率与开发者体验（以速度衡量）之间的权衡关系会呈现在一张图表中，方便决策。我们将使用下面的图表来展示，随着用户并发量的增加，不同的模型/硬件组合如何接近其能产生的最大 token 输出，同时我们也会密切关注开发者需要等待任务解决的时间。

理解这些数值将帮助您更好地了解不同选项在性能和开发者体验上的差异，从而找到最适合您组织需求的方案。

在过去的几周里，我们的团队一直在努力工作，对 SWEBench Pro 中精选的 64 个真实编程任务进行了约 100 次测试，测试采用了不同且合适的硬件配置，以精确计算各项指标（每个任务的中位时间、每秒每设备的 token 数等）。在 Artificial Analysis [9] 的开源权重质量排名指导下，我们将每个硬件层级与符合其内存预算的领先模型进行了匹配：

  • DeepSeek-V4-Flash 在 4×H200 上，使用 vLLM 服务
  • GLM-5.2 在 8×B200 机架上，使用 SGLang 服务
  • Qwen3.6-35B-A3B-FP8 在 NVIDIA 的 DGX Spark 上，使用 vLLM 服务

在接下来的章节中，我们将深入探讨实际结果，并通过成本分析进行总结，对比自购 GPU、租用 GPU 以及从前沿模型提供商或开源权重 API 提供商购买 token 的成本。我们认为，许多组织目前正在思考这些问题，而我们希望为您提供解答这些问题的工具。

04

从桌上的 Spark 到 8×B200 节点：该买哪款设备

如果您有兴趣租用或购买硬件，有几种选择可供考虑。下面我们介绍四种热门的候选方案，我们将在本文中多次提及它们。每种方案都搭配了一款最适合该硬件的开源权重顶级模型。

您会发现我们在这里重点介绍了 NVIDIA，这在很大程度上是因为我们能够轻松获取到他们的设备。其他供应商肯定也有类似的替代方案，我们将在后续的文章中进行讨论。目前，请将这些方案视为参考选择，而非特定的推荐。

  • 让我们从最便宜的选择开始，一台 NVIDIA DGX Spark。这是为那些想尝试自托管但又不想和采购部门打交道的团队准备的设备：它可以放在桌面上，价格还不到一次会议旅行的费用。它可以容纳 Qwen3.6-35B-A3B（简称“Qwen3.6”）。对于这样的机器来说，这已经是个相当大的模型了——我们将在文章后面看到它在开发者体验方面的表现。
  • 接下来是 NVIDIA H200，一个功能强大的单加速器。也许有点出人意料的是，与 DGX Spark 相比，它实际上能让你托管的大模型并没有多太多。这主要取决于可用内存（DGX Spark 为 128GB，而 H200 为 141GB）。然而，你确实能得到一个更大的 token 池，这意味着在更高并发的情况下吞吐速度会更快。
  • 如果你想托管更强大的模型，但又不想完全破费，那么搭载 4 个 H200 的 NVIDIA HGX H200 是一个不错的选择。有了 4 个 H200，你可以托管更大的模型，比如 DeepSeek-V4-Flash，它在速度、并发和质量方面提供了一个非常好的平衡点。
  • 再上一个台阶，搭载 8 个 B200 的 HGX B200 是一个强大的参考系统，因为它能让你运行最先进的开源模型，比如在质量上目前最接近前沿模型的 GLM-5.2。如果你的首要考虑是质量，这就是你的选择。

在撰写本文时，Kimi 的 K3 模型引起了广泛关注，因为早期的基准测试（有待进一步确认）表明，它的性能可以与 Anthropic 的 Fable 模型相媲美，但成本要低得多。目前，我们的团队正在等待这个模型在本月底发布开源权重，以评估在自己的基础设施上运行这个 2.8T 模型需要什么条件。更多相关信息即将揭晓。

接下来，我们将从开发者体验、成本以及它们能容纳的模型质量这几个方面，对这些竞争者进行测试。让我们开始吧。

05

这些池子有多大？

那么，把一台 DGX Spark 放在触手可及的桌面上怎么样呢？嗯，不出所料，它的 token 池并不大。在我们的测试中，我们无法让它支持超过 1-2 个并发用户，并且遇到了大量超时错误之类的问题。如果你对 Qwen3.6 感到满意，它可能适合你，但不要指望它在速度、并发或模型质量上能有所扩展。这表明——尽管 LinkedIn 上的标题很吸引人——我们还远未达到可以在经济实惠的台式机上直接下载前沿智能模型的程度。像代码补全这样简单的任务？问题就不那么大了。

这就是多花点钱购买专业版 H200 的价值所在，对于同一模型，它在处理 Qwen3.6 时每秒能生成至少 30 倍的 tokens。实际上，不要对 Qwen3.6 能生成这么多 tokens 感到惊讶，即便在单张 H200 上——它仍然是个相当小（因此能力也较弱）的模型。我们还可以看到，在 HGX H200 上的 DeepSeek-V4-Flash 拥有更大的 token 池（当然是在 4 张 H200 的配置下），但只有在高并发情况下才能发挥其潜力。相比之下，尽管 GLM-5.2 运行在我们测试中最强大的硬件上（HGX B200），但其 token 池却更小。确实，16 个并发会话似乎就差不多能让 GPU 满负荷运转，而 GLM-5.2 的总吞吐量仅为每秒约 175 tokens。更大、更强大的模型往往伴随着更小的 token 池，而我们选择的硬件并不能完全弥补这一点。

你可能注意到了一些令人惊讶且不安的现象——有些线条不是逐渐趋于平稳，而是直接断崖式下跌。在探讨开发者体验之后，我们会再详细分析这个问题。

06

我的开发者对速度的满意度如何？

你可能不会希望将 token 池用到极限，因为单个开发者可能会觉得你的解决方案与他们信赖的 Codex 或 Claude 助手相比慢得像蜗牛。以后两者为基准，我们可以看到，尽管有强大的 HGX B200 硬件支持，GLM-5.2 从 8 个并发会话开始就表现吃力。正如其相对较小的 token 池所显示的，大规模部署前沿模型是一项极具挑战性的任务。在另一端，DGX Spark 即便只有 1 个用户也很慢，对于多用户场景更是完全无法使用。

DeepSeek-V4-Flash 和 Qwen3.6 都能坚持更久，最多支持到 32 个用户，然后性能急剧下降。请注意，DeepSeek-V4-Flash 的性能接近 Qwen3.6-35B-A3B，但它运行在更昂贵的硬件上——通过这项投资换取更高质量的输出，同时保持负载下的速度。当然，与 GLM-5.2 相比，你付出的代价是质量较低，这一点我们稍后会详细讨论。

所以大致来说，在这些配置下，你可以预期在开发者开始抱怨速度问题并找上门之前，最多能支持以下数量的并发用户：

型号舒适并发数
Qwen3.6 (DGX Spark)仅 1 个 — 而且速度仍然很慢，比 Claude Code 慢了近 3 倍
Qwen3.6 (H200)轻松支持 32 个，在 48 个并发时比 Claude Code 慢 2 倍

现在我们来谈谈房间里的大象：在这张图和接下来的图中，你都会看到 Qwen3.6 在 H200 上和 DeepSeek-V4-Flash 在 HGX H200 上，在并发数达到 48 和 64 后性能急剧下降。这很令人意外，因为从直觉上你不会期望看到这种情况，理论上这些曲线应该会收敛到 GPU 的最大输出。那么为什么我们这么早就看到了性能崩溃呢？原因在于推理引擎（vLLM）的具体细节、其默认参数，以及它在 prefill 和 decode 请求之间如何平衡计算，还有像有效 KV-cache 大小及其使用率等重要资源。

此外，你可能对 GLM-5.2 提供的并发水平感到失望。一个可能的原因是使用了 speculative decoding（推测解码），这种技术可以在低并发时加速 token 生成，但在高并发时反而可能损害性能。

但别太快灰心，如果你针对你的工作负载优化推理引擎（例如 vLLM），就能更好地处理这些问题，从系统中获得更多收益——我们将在下一篇博文中深入解释和讨论这一点。

回到图表。请注意，在这些并发水平下，即使能让你的开发者满意，你仍然没有充分利用系统的潜力。我们可以将之前图表的信息整合到一张图中，以突出显示每个系统的这种差距。例如，对于 HGX H200 上的 DeepSeek-V4-Flash，在 c=32 且开发者满意的情况下，你只使用了 1381 tokens/s，而 c=64 的池子是 1717 tokens/s，多了 24%。

请注意这种权衡，虽然你可以在实际应用中调整它，但不要简单地期望你能像广告宣传的那样从系统中获得全部的池子性能。

07

这一切要花多少钱？

当涉及到如何投资你的 AI 编码助手时，你的选择并不仅限于坚持使用你选择的模型 API 提供商，或者直接购买硬件。还有一个选择是租用 GPU，供应商从超大规模云服务商到新锐云服务商、AI 工厂或其他各方都有。每种选择都有不同的价格，但也提供不同的保证、服务和集成方案。

一如既往，模型质量至关重要。为了公平比较，我们还针对不同模型提供商的官方 API 重新运行了 SWEBench Pro 任务集，并跟踪了 token 成本。对于购买或租用硬件，成本取决于运行此类任务集所需的时间。如前所述，这取决于并发性。对于每个系统，我们从成本角度选择最佳并发性，即能最优化使用 GPU 的方案。请注意，这可能是影响用户体验的一个因素。

我们没有在此次比较中包含 DGX Spark，因为其在定价和性能方面确实是一个不同的类别。Qwen3.6 的购买/租用成本基于 1 个 H200，DeepSeek-V4-Flash 基于 HGX 4xH200，GLM-5.2 基于 HGX 8xB200。我们将这些成本分摊到 5 年，但不包括额外的电力或维护成本，因为这些成本在很大程度上取决于具体组织情况。

*硬件购买和租用价格为截至 2026 年 7 月的公开广告费率 [10][11][12][13]。

相同的工作负载，却得到了三个截然不同的答案。从我们的计算中得出的最有趣的相关结论是：一个 4×H200 服务器必须保持 89% 的忙碌状态（全天候，持续五年），其拥有成本才能低于 DeepSeek 的 $2.13 账单；而 B200 服务器机架只需 15% 的利用率就能超越前沿 API，并且以租用价格计算，其前沿质量任务的单位成本已降至 $1.11（租用成本除以 64 个任务），比任何 API 收费都便宜。

如果您低于例如 15% 的利用率阈值，租用 GPU 可能是一个更好、更经济的选择，因为它允许您在非高峰时段关闭使用。是这样吗？嗯，令人惊讶的是，这很大程度上取决于模型类型。对于 Qwen3.6，租用 GPU 比 API 方案便宜 35 倍。对于 GLM 5.2，我们也看到了成本降低，尽管幅度较小，为 23%。然而，对于 DeepSeek，情况则完全相反。如果没有针对您的工作负载进行任何优化，其成本实际上远高于 DeepSeek 自身的 API。

在做成本决策时，真正重要的不是开源与闭源的争论，而是运行你特定工作负载的实际成本。对于代码助手来说，高达98%的输入令牌都会被缓存，而这正是 DeepSeek-V4-Flash API 的定价能够以压倒性优势击败更小的 Qwen3.6 模型的原因所在。

没有绝对的赢家。按实际使用量计价的情况下，只有当设备保持高负载时，购买才划算——4×H200 需要保持 89% 的负载，而 B200 机架只需 15%。低于这个负载，租用或廉价的开放权重 API 往往更划算。购买 GPU 是为了那些账单无法衡量的东西——控制权、隐私、延迟——而不是仅仅为了省钱。

08

但我喜欢实验室里的闭源前沿模型？

你并非唯一这么想的人。然而你正在阅读这篇文章，考虑如何逐步远离它们。说实话，虽然开放权重模型在 Anthropic、OpenAI 或 Google 的前沿模型发布后总会滞后几个月，但在2026年，最好的开放权重模型已经变得非常实用。此外，随着 GLM 5.2 和 Kimi K3 等新模型的发布，开放权重与闭源模型之间的差距正在迅速缩小。对于这些模型（如 GLM-5.2），你至少需要一台 HGX B200 系统。不要指望使用 H200 甚至 4xH200 能获得相同的性能。

开放权重与闭源模型之间的差距正在迅速缩小。

对于我们运行的任务，我们通过 Artificial Analysis [9] 等模型质量评估机构的普遍见解进行了验证。为完整起见，以下是在我们的 SWE Bench Pro 64 个任务样本中，使用 Claude Code 作为测试工具时，各模型的解决率（所有运行和并发情况下的汇总数据）。

09

那么一个 GPU 能容纳多少开发者？

介于 0 到 64 之间。或者至少根据我们查看的配置情况——但关键在于它是一个范围。如果你认真考虑投资自己的硬件，以下是一些可能相关的关键要点。

  • 你的 DGX Spark 实际上只适合单次使用。 在理想情况下，它最多只能容纳一名开发者运行小型模型，并且需要适中的 token 池。如果你追求的是大规模扩展，这并不是最佳选择。但如果你只是想在中等规模任务上获得良好的个人开发体验，它是一台非常得力的工具。
  • 然而，单张 H200 运行 Qwen3.6 就能轻松支持 32 个并发会话，而 4 张 H200 配合 DeepSeek-V4-Flash 可以在更高画质下实现同样的效果。将 8 张 B200 组合在一起，你的团队就能部署接近前沿的模型（如 GLM-5.2）——但任务执行速度会突然变得极其缓慢，最多只能支持 8 名开发者。
  • 租用 GPU 可能确实能节省成本，但这高度依赖具体模型。 我们的测试显示，使用 Qwen 时成本最多可降低 35 倍（！），但使用 DeepSeek 时成本反而高于 API 调用。这表明，合理的工作量与模型、硬件的匹配至关重要，而且在不同基础设施间切换并非简单的成本优化决策。
  • 如果你的工作量超过某个阈值，自购硬件可能变得划算。 这取决于你的组织对质量、速度和成本的实际需求。如果你的工作量能让租用的 B200 机架保持 15% 的利用率，那么——令人惊讶的是——你已经在用接近前沿的模型质量，击败了前沿 API 的定价。如果达不到这个利用率，仅仅为了节省 token 费用而自托管是不明智的，因为闲置的 GPU 机架每任务成本反而高于你当前的 API 账单。当然，数据敏感性等其他因素也可能影响决策。

当然，实际情况可能因人而异。因此，请务必测量自己的实际工作量，了解峰值需求，并随着组织逐步采用 AI 编程助手持续跟踪这些数据。虽然当前数据可能指向使用 API，但几个月后情况可能大不相同。在此期间，我们会持续开发工具和提供洞察，帮助你解决这个难题。

如果你想让更多开发者在同一硬件上高效工作，我们接下来的文章将专门讨论这个话题：如何调整推理引擎以适配你的工作负载，有时能让单台设备的性能翻倍。敬请关注。

附录：我们的研究方法

我们的核心理念是，在考虑 AI 技术栈（包括软件和硬件）时，实际工作负载的细节至关重要。为了衡量这一点，我们搭建了一个尽可能模拟智能编程代理行为的系统。系统中可配置的部分，一方面是推理引擎：

  • 底层硬件。我们测试了
    • 放在我们桌上的 DGX Spark（联想 ThinkStation PGX）
    • 托管在我们本地数据中心的一块 H200（配备 24 个 CPU 核心和 64GB 内存）
    • 通过 NVLink 连接、托管在我们本地数据中心的 HGX 4xH200
    • 由专用 AI 云基础设施提供商托管的 HGX 8xB200
  • 不同的模型，如讨论中提到的
    • 在 DGX Spark 上运行 Qwen3.6-35B-A3B，使用 https://recipes.vllm.ai 上的 vLLM 配置（采用 MTP 推理解码）
    • 在 H200 上运行 Qwen3.6-35B-A3B，使用 https://recipes.vllm.ai 上的 vLLM 配置（采用 MTP 推理解码）
    • 托管时使用 4 张张量并行和 https://recipes.vllm.ai 上的 vLLM 配置运行 DeepSeek-V4-Flash（我们调整了 8xH200 的配置，采用 MTP 推理解码）
    • 托管时使用 8 张张量并行和 https://modal.com/blog/introducing-auto-endpoints 推荐的 SGLang 配置运行 GLM-5.2（采用 EAGLE 推理解码）

另一方面，我们需要模拟工作负载，可以配置

  • 并行运行智能编程任务的工作者数量。这些是不同的 Docker 容器，每个容器从 Harbor 任务格式[reference]中获取一个编程任务。这些工作者托管在沙盒提供商的基础设施上，并在通用 CPU 上运行。
  • 每次任务运行包含三个阶段。
    • 设置阶段，确保已安装所有先决条件
    • 实际的代码生成循环，向推理端点发送请求
    • 最终评估，检查生成的代码是否通过测试
  • 我们选择不删除第一和第二阶段，因为它们基本模拟了开发人员在编码之外的工作——比如在两个任务之间喝杯咖啡。不过，在需要不同分析时，我们可以将它们分开。例如，我们图表中的任务时间仅报告实际的代码生成时间。包含设置和评估阶段会降低端点的有效并发性，因为任何时候都有一些代理处于这些阶段，而不是在发送请求。
  • 作为固定的任务集，我们从 ScaleLabs 的 SWEBench Pro 中采样了 64 个任务。我们使用自己的平台来编排这些任务，但已复现了使用 Harbor 获得的数字，以确保准确性。

在推理引擎和工作节点上，我们捕获了大量指标，这些指标能够深入分析工作负载与底层软硬件推理栈的交互情况。这些指标帮助我们进一步优化各项设置，以便在同一个 GPU 上容纳更多开发者。我们将在下一篇博客文章中详细讨论这一点。

为了测量 tokens/s，我们关注任务集主体部分的持续吞吐量，例如在队列末尾（此时只剩下少数未完成的任务）的数据会被排除。需要注意的是，存在一些短暂的峰值会高得多（尤其是 GLM-5.2），但在测试的工作负载中，这些峰值无法长时间保持稳定。

观察结果存在一定差异，虽然 tokens/s、任务时间和解决率的差异较小（我们在所有运行中取平均值），但在高并发情况下，Qwen3.6 和 DeepSeek-V4-Flash 吞吐量崩溃的发生率差异尤为明显。这与使用大量工作节点时请求的随机性有关。我们选择选择发生这种情况的最低并发级别，因为这表明该配置已不再适用于生产环境。
