周二是 无状态 MCP 日 - MCP 2.0 的发布，或者用更正式但不太好记的名字来说，就是 2026-07-28 模型上下文协议规范。这是 MCP 规范自首次发布以来最重大的变化，也重新点燃了我对这个协议的个人兴趣。

背景介绍：MCP 是模型上下文协议（Model Context Protocol），它描述了一种向基于大语言模型的智能体框架暴露新工具的标准方式。该协议由 Anthropic 在 2024 年 11 月首次推出，在 2025 年的大部分时间里引起了 巨大的关注热潮，但随着人们发现一个拥有终端和 curl 访问能力的智能体框架能以更灵活的方式完成 MCP 大部分功能后，MCP 的热度便被 Skills（另一项 Anthropic 的发明）所超越。我在 2025 年回顾文章中写过相关内容。

我现在重新关注 MCP。给智能体一个能访问互联网的 shell 环境 风险重重，并且需要一个强大的模型来有效驱动这样的环境。MCP 工具更容易审计和控制，而且足够简单，以至于在笔记本电脑上运行的小型模型也能很好地驱动它们。

新的无状态 MCP 规范也大大降低了实现该协议客户端和服务器的复杂度。我这周就搭建了三个！

无状态 MCP 带来了哪些便利

有状态和无状态 MCP 之间最好的区别演示，出现在这篇介绍新规范候选版本的 5 月 21 日博客文章中。文章包含了一个清晰的“之前与之后”的对比示例。

旧的有状态 MCP（我称之为“传统 MCP”）需要两次 HTTP 请求——第一次用于初始化会话并获取一个 Mcp-Session-Id，第二次才是实际调用工具：

POST /mcp HTTP/1.1
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "capabilities": {
    },
    "clientInfo": {
      "name": "my-app",
      "version": "1.0"
    }
  }
}

POST /mcp HTTP/1.1
Mcp-Session-Id: 1868a90c-3a3f-4f5b
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": {
      "q": "otters"
    }
  }
}

这种新的无状态方式使用单个 HTTP 请求，看起来是这样的：

POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search",
    "arguments": {
      "q": "otters"
    },
    "_meta": {
      "io.modelcontextprotocol/clientInfo": {
        "name": "my-app",
        "version": "1.0"
      }
    }
  }
}

从客户端和服务器端的实现角度来看，这要简洁得多。它也更适合构建可扩展的 Web 应用程序，因为现在你无需维护服务器端状态来跟踪那些会话 ID，也无需担心将同一个会话路由到同一个后端机器上。

mcp-explorer

我找不到一个很好的 CLI 工具来交互式地探测 MCP 服务器，所以我让 Codex 帮我构建了一个自己的工具。

mcp-explorer 就是成果。它是一个无状态的 Python CLI 工具，所以你甚至不需要安装就可以试用——它可以像这样与 uvx 一起使用：

uvx mcp-explorer list https://agentic-mermaid.dev/mcp

这个命令会查询 Ade Oshineye 的 agentic-mermaid.dev 演示 MCP。上面的命令会返回以下工具列表：

execute(code: string, timeoutMs?: integer) - 执行 Mermaid SDK 代码
  在隔离的沙箱中运行 JavaScript；返回一个值。

describe_sdk(family: string, detail?: string) - 描述 Mermaid SDK 操作
  返回与版本匹配的图表家族的变更操作。

render_svg(source: string, options?: object) - 将 Mermaid 渲染为 SVG
  将 Mermaid 源字符串渲染为可主题化的 SVG。返回 { ok, svg }。

render_ascii(source: string, useAscii?: boolean, targetWidth?: integer, options?: object) - 将 Mermaid 渲染为文本
  将 Mermaid 源字符串渲染为文本。返回 { ok, text }。

render_png(source: string, scale?: number, background?: string, fitTo?: object, options?: object) - 将 Mermaid 渲染为 PNG
  将 Mermaid 源栅格化为 PNG。返回 { ok, png_base64 }。
...

然后检查一个工具：

uvx mcp-explorer inspect render_svg

这会输出大量信息，包括输入和输出的 JSON schema。

调用该工具并向其传递参数：

uvx mcp-explorer call \
  https://agentic-mermaid.dev/mcp \
  render_svg \
  -a source 'graph TD; A-->B' \
  -a options '{"padding":24}'

返回结果如下：

{"ok":true,"svg":"<svg xmlns=\"http://www.w3.org/2000/svg\" width=...

README 中还有 更多命令，但你应该已经明白大概意思了。我发现构建这样的 CLI 工具是熟悉规范的一种非常高效的方式，即使大部分实际代码是由代理生成的。

datasette-mcp

第二个项目是 datasette-mcp，一个 Datasette 插件，为任何 Datasette 实例添加一个 /-/mcp 端点。

这大概是我第四次尝试构建这个插件了，但得益于新的无状态 MCP 规范，我终于有了一个可以放心发布的版本。

它只提供了三个工具：list_databases()、get_database_schema(database_name) 和 execute_sql(database_name, sql)。这些工具的功能完全如其名所示——不过 execute_sql() 目前是只读的。

将它们集成到代理程序或 ChatGPT、Claude 这样的聊天工具中，这些工具就能获得针对你的托管 Datasette 实例运行 SQL 查询的能力。

目前我正在我的博客 Datasette 镜像上运行它，地址是 datasette.simonwillison.net/-/mcp。花了不少功夫才搞清楚如何将它连接到 ChatGPT 和 Claude，但最终还是成功了。这篇 新的 TIL 文章 详细展示了具体操作方法。

MCP 是一种更安全的智能体构建方式

MCP 刚发布几个月后，我写了篇 《模型上下文协议存在提示注入安全问题》，文中指出，让终端用户自由组合工具的模式，将防范数据泄露攻击的责任推给了用户自己。那时我还没提出 “致命三重奏” 这个概念，但那正是我当时的核心担忧。

后来出现了可以随意访问 shell 和 curl 的通用智能体，这让安全问题变得更加棘手！

我逐渐认识到 MCP 的一个优点：与在开放网络环境中执行任意命令（目前大多数通用和编程智能体工具的默认模式）相比，更容易推理智能体的能力边界以及可能出现的风险。

未来在基于 LLM 构建敏感应用时，我计划更多地采用 MCP。
